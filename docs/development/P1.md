# P1 — Provider Architecture Stabilization

**Status:** LOCKED  
**Type:** Architecture stabilization  
**Purpose:** Converge Linlin Agent on one canonical Provider registration, construction, and management path while preserving existing provider behavior.

## 1. Objective

Establish and verify the canonical flow:

`ProviderRegistry → ProviderFactory → ProviderManager → BaseProvider → Provider Adapter`

Remove or isolate duplicate/competing provider-factory or registry paths only when proven redundant. Do not add new providers in this phase.

## 2. Required Reading

- `AI_COLLABORATION_CHARTER.md`
- `AGENTS.md`
- `docs/standards/Engineering_Standard.md`
- `docs/standards/Testing_Standard.md`
- `docs/architecture/System_Architecture.md`
- this file
- accepted ADRs/RFCs that govern Provider Runtime, if present

## 3. Allowed Work

- provider registry/factory/manager/base abstractions;
- provider adapter registration and construction fixes;
- duplicate registration/factory cleanup when safely proven;
- provider capability metadata normalization;
- provider-focused unit/integration tests;
- minimal import/config changes required by this architecture.

Recommended capability metadata includes, when applicable:

- `supports_chat`
- `supports_stream`
- `supports_tools`
- `supports_embeddings`
- `supports_vision`
- `requires_api_key`
- `local`
- `experimental`

## 4. Forbidden Work

- adding new providers;
- changing cloud pricing/free-tier claims;
- ToolLoop redesign;
- ToolParser redesign except import/interface compatibility required by P1;
- Memory/RAG/MCP/Scheduler/Plugin development;
- UI redesign;
- framework replacement;
- broad provider rewrites unrelated to canonical routing.

## 5. Architecture Invariants

- all providers implement the canonical `BaseProvider` contract;
- only one authoritative provider registry exists at runtime;
- only one authoritative provider-construction route exists at runtime;
- Provider Runtime does not execute tools directly;
- provider-specific behavior remains inside adapters.

## 6. Deliverables

- documented canonical provider call path;
- duplicate/legacy paths removed or clearly deprecated only when safe;
- normalized capability metadata;
- regression tests proving provider registration and construction behavior.

## 7. Acceptance Criteria

- no ambiguous `registry` vs `provider_registry` runtime path remains;
- existing supported providers can be discovered/constructed through the canonical path;
- invalid provider names fail predictably;
- provider capability data is consistent and test-covered;
- no P2 tool-calling behavior is implemented early;
- P0 validation remains green.

```bash
python -m compileall app tests

```

Run frontend validation only if P1 legitimately affects frontend provider selection/configuration.

Report old vs canonical provider path, modified files, removed/deprecated duplicate paths, tests/results, compatibility risks, and remaining issues.
