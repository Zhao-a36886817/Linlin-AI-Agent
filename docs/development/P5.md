# P5 — Credential and Secret Storage Security

**Status:** LOCKED  
**Type:** Security architecture  
**Purpose:** Provide a clean credential abstraction that prevents API keys and secrets from being persisted or exposed insecurely.

## 1. Objective

Stabilize `CredentialStore` behind a clear interface with secure OS-backed storage where available and a non-persistent session fallback when secure persistence is unavailable.

## 3. Allowed Work

- CredentialStore interface/implementation repair;
- OS credential/keyring adapter integration;
- in-memory/session-only fallback;
- secret redaction in logs/errors/API serialization;
- migration away from plaintext config storage;
- credential-focused tests;
- minimal settings/API changes required to use the store safely.

## 4. Forbidden Work

- inventing custom cryptography without an approved security design;
- deriving long-term encryption keys from predictable identifiers such as UID/username alone;
- storing secrets in committed `.env`, JSON provider config, frontend storage, logs, chat history, or test fixtures;
- silently persisting plaintext when secure storage is unavailable;
- unrelated Provider feature additions.

## 5. Architecture Invariants

- callers request credentials through the CredentialStore abstraction;
- provider configuration may reference credential identifiers but not raw persisted secrets;
- frontend must never receive secrets unless a specifically approved design requires it;
- secret values are redacted from logs and diagnostic structures.

## 6. Deliverables

- clean CredentialStore contract;
- secure OS-backed backend where available;
- session-only fallback policy;
- secret-redaction tests;
- documented behavior when secure persistent storage is unavailable.

## 7. Acceptance Criteria

- no raw API key is persisted in normal provider configuration;
- no raw API key appears in application logs or serialized provider status;
- fallback behavior is explicit and non-persistent unless a separately approved secure backend exists;
- credential retrieval failure is handled predictably;
- P0-P4 validation remains green.
