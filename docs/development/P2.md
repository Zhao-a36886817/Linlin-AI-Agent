# P2 — Ollama and Tool Calling Reference Stabilization

**Status:** LOCKED  
**Type:** Provider/tool integration stabilization  
**Purpose:** Make Ollama the reference local provider for reliable chat, streaming, and model→tool→result→final-answer execution.

## 1. Objective

Stabilize the existing Ollama adapter and ToolLoop integration while preserving the Universal ToolParser as the normalization layer.

Reference flow:

`User → ProviderManager → Ollama → ToolParser → ToolLoop → Tool Runtime → Tool Result → Ollama → Final Answer`

## 3. Allowed Work

- Ollama adapter chat/stream/tool-call handling;
- Universal ToolParser bug fixes and regression tests;
- ToolLoop changes strictly required for correct tool round trips;
- normalization of native and text-encoded tool calls;
- removal or gating of noisy debug prints;
- separation of thinking/reasoning metadata from final user-facing content;
- reliable tool-mode option handling.

For models where thinking can consume the tool-call budget, tool mode SHOULD default to non-thinking behavior unless explicitly requested and proven compatible. This must be implemented as capability-aware behavior, not a brittle model-name hack.

## 4. Forbidden Work

- Provider architecture redesign;
- new cloud providers;
- new Tool categories;
- Memory/RAG/MCP/Scheduler/Plugin work;
- UI redesign;
- hard-coding one specific Ollama model as a universal requirement.

## 5. Architecture Invariants

- Universal ToolParser remains the tool-call normalization layer;
- Provider adapters parse/normalize responses but do not execute tools;
- ToolLoop owns the iterative model/tool orchestration;
- Tool Runtime owns tool execution;
- streaming and non-streaming paths expose coherent semantics.

## 6. Deliverables

- stable Ollama chat path;
- stable Ollama stream path;
- stable native/text tool-call parsing;
- regression coverage for supported ToolParser formats;
- deterministic tool-loop tests that do not require internet access;
- optional live Ollama validation when Ollama is available.

## 7. Acceptance Criteria

- calculator-style model→tool→result→final-answer loop passes;
- native tool calls and supported textual fallback formats parse correctly;
- tool mode does not silently exhaust output on hidden thinking when non-thinking is required;
- streaming does not incorrectly mix internal thinking into final content;
- tests do not require a specific model to be installed in CI;
- P0/P1 validation remains green.
